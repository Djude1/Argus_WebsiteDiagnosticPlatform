# 掃描各階段做了哪些檢測（依執行順序）

> 對照程式：`backend/apps/scans/tasks.py` 的 `SCAN_PIPELINE`（執行順序）與 `planned_scan_steps`（進度條上的階段），各階段實作檔案寫在每一節開頭。2026-10-10 依程式整理；**改了規則、門檻或嚴重度時同步本檔**。

### 為什麼 SEO／AEO／GEO／UX／資安五個階段幾秒就跑完

這五個階段**不連線、不開瀏覽器**，只把「爬取」階段已經抓回來的 HTML 與量測結果拿來比對規則。開網頁、等渲染、截圖、量行動版版面、跑無障礙檢查這些花時間的工作，都在爬取階段每頁做一次。20 頁 × 5 個維度＝100 次規則比對，加起來幾秒是正常的；準確度取決於規則與證據，不是花的時間。

### 嚴重度與扣分

| 嚴重度 | 扣分權重 | 說明 |
|---|---|---|
| 嚴重 | 60 | 已過期憑證、外洩的環境變數檔、確認可利用的注入 |
| 高 | 35 | 外洩身分證／信用卡、弱 TLS、SPF +all |
| 中 | 12 | 缺 HSTS、CSRF、Cookie 沒有 Secure |
| 低 | 4 | 缺 CSP、缺 Open Graph、觸控目標過小 |
| 資訊 | 0 | 只是提醒，不扣分 |

## 0. 等待排程

任務建立後先預扣點數，送進背景佇列，等掃描程式（Celery worker）接手。這個階段不做任何檢測。

## 驗證目標（不顯示）

`stage_validate_target`：再次確認網址是公開的 http／https 網址。localhost、內網 IP、帳密寫在網址裡、非 80／443 埠一律拒絕，避免被拿來打內部網路。

## 1. 爬取

`crawler.py`。用真實 Chromium 瀏覽器走訪同一個網站的頁面，**後面所有逐頁檢查都只用這裡收集的資料**。

**走訪範圍**

| 項目 | 規則 |
|---|---|
| 起點 | 使用者輸入的網址 |
| 範圍 | 單頁＝只看這一頁；全網站＝最多 50 頁（頁數上限）、深度 6 層 |
| 同網站 | 只走同一個協定＋網域＋埠；跳到別的網站就停 |
| sitemap | 全網站模式先讀 robots.txt 宣告的 sitemap（或 `/sitemap.xml`）補種子，連結少的網站也能爬滿 |
| robots.txt | 預設遵守 `Disallow`，被禁止的頁面不爬（記在爬取紀錄） |
| 速度 | 被動模式每秒最多 5 個請求、主動模式 2 個 |
| 不爬 | `/cdn-cgi/`（Cloudflare 陷阱連結）、超大檔案 |

**每一頁收集的資料**

| 收集項目 | 給哪個階段用 |
|---|---|
| HTTP 狀態碼、回應標頭、最終網址、轉址 | SEO、資安、站台資安 |
| 原始 HTML 與執行 JavaScript 後的 HTML | 全部逐頁檢查、AEO 問答、GEO |
| 等畫面穩定（每 250ms 量正文字數與元素數，連續兩次不變才算就緒，最多 5 秒） | 避免抓到還沒載入完的內容 |
| 載入時間 | 網站概況「網站優勢」 |
| 版面跳動（CLS）與移動的元素 | UX |
| 整頁截圖 | 結果頁截圖、標註 |
| axe-core 無障礙檢查（WCAG 2.0／2.1／2.2 A、AA，每頁最多 15 秒） | UX |
| 頁面上未捕捉的 JavaScript 錯誤 | UX |
| 切到手機寬度：是否破版、觸控目標大小、欄位標籤、行動版截圖 | UX |
| 頁面背景發出的 API 請求（XHR／fetch） | 網站特徵、主動測試 |
| robots.txt、llms.txt、sitemap 原文 | SEO、GEO、敏感檔案 |
| 主動模式＋勾資安＋啟用 ZAP 時錄製同網站的流量（HAR） | ZAP 被動分析 |

**被阻擋的判斷**：401、403、429、Cloudflare 驗證頁、超大頁面會標成「被阻擋」，不拿來分析，但仍拍截圖讓人核對。**一頁都抓不到時，整個掃描標失敗並全額退點**，不會產生看起來正常的分數。

## 進入檢查、網站特徵、啟動效能量測（不顯示）

- **進入檢查**：記錄爬取警告、把頁面寫進資料庫、狀態改為「檢查中」。
- **網站特徵**（`fingerprint.py`）：只用已抓到的資料判斷 CMS（WordPress、Drupal、Shopify…）、前端框架、伺服器、CDN、有沒有登入頁、API、檔案上傳。只記錄，不影響掃描與計分。
- **啟動效能量測**：勾 UX 且平台有 PageSpeed 金鑰時，這時就在背景請 Google 開始量測，和後面的階段同時進行。

## 2. SEO（逐頁）

`scanners.analyze_seo`。登入、註冊、後台頁面與 PDF 等檔案不檢查。

| 檢查 | 判定標準 | 嚴重度 |
|---|---|---|
| 標題（title）長度 | 少於 10 或超過 65 字元 | 低 |
| Meta description | 沒有，或少於 50／超過 160 字元 | 低 |
| H1 | 沒有 H1＝低；超過一個＝資訊（HTML 與 Google 都允許多個） | 低／資訊 |
| 圖片替代文字 | 有圖片沒寫 `alt`＝低；3 張以上大圖 `alt=""`（可能是漏寫）＝資訊 | 低／資訊 |
| canonical | 沒有 `<link rel="canonical">` | 資訊 |
| Open Graph | 缺 og:title、og:description、og:image、og:url 任一個（社群分享沒有預覽卡片） | 低 |
| 結構化資料必填欄位 | 已有 JSON-LD，但缺 Google 複合式搜尋結果要求的必填欄位（依 Google Search Central；不檢查 Google 已停用的 FAQPage／HowTo） | 低 |
| 自評星等 | 商家在自己網站標的評分，Google 不會顯示成搜尋星等 | 資訊 |

## 3. AEO（逐頁）

`aeo/page_checks.py`。檢查內容能不能被搜尋引擎與 AI 摘要、引用。

| 檢查 | 判定標準 | 嚴重度 |
|---|---|---|
| 不可被索引 | meta robots、googlebot 或 `X-Robots-Tag` 有 `noindex` | 中 |
| 禁止摘要 | `nosnippet` 或 `max-snippet:0` | 中 |
| 部分段落禁止摘要 | 有 `data-nosnippet` 區塊 | 資訊 |
| JSON-LD 語法錯誤 | 結構化資料無法解析，整段會被搜尋引擎忽略 | 中 |
| 標記與頁面不一致 | 結構化資料寫的值（電話、地址、價格…）在頁面看得到的文字裡找不到 | 低 |

AEO 分數主要來自後面的「AEO 問答檢測」。

## 4. GEO（逐頁）

`scanners.analyze_geo`、`analyze_geo_fast`、`geo_structure.py`、`geo_citability.py`。檢查內容是否容易被生成式 AI 理解與引用。

| 檢查 | 判定標準 | 嚴重度 |
|---|---|---|
| 沒有結構化資料 | 頁面沒有任何 JSON-LD | 低 |
| 實體類型不明確 | 有 JSON-LD，但沒有 Organization、LocalBusiness、Article、Product 等明確類型 | 資訊 |
| 可引用段落偏少 | 成句段落少於 2 段，或正文不到 300 字 | 資訊 |
| 內容依賴 JavaScript | 執行 JS 後正文 ≥400 字，但原始 HTML 不到一半（多數 AI 爬蟲不執行 JS） | 中 |
| 沒有主內容區塊 | 沒有 `<main>` | 低 |
| 段落過長 | 有超過 1000 字的段落 | 低 |
| 長文沒有小標題 | 成句段落合計約中文 1500 字／英文 1000 詞以上，卻沒有 h2～h6 | 低 |
| 列舉沒用清單 | 同一段裡有 3 個以上編號（1. 2. 3.） | 資訊 |
| 缺少權威來源引用 | 有篇幅的正文頁沒有連到政府／學術等權威來源、沒有 `<cite>`、沒有「參考資料」區塊（Princeton 研究：附來源最多 +115% 被引用率） | 低 |
| 缺少量化數據 | 有篇幅的正文頁幾乎沒有百分比、金額等具體數字 | 資訊 |
| 缺少可引用引言 | 有篇幅的正文頁沒有 blockquote 或署名引言 | 資訊 |
| 內容可能過時 | 有篇幅的正文頁同時出現過去年份、時效性措辭、軟體版本、定期價格等 ≥2 類會變動的內容，卻沒有更新日期訊號 | 資訊 |
| 區段偏長不利分塊 | 有小標題、但正文很長、平均每個小標題區段仍超過約 280 字，AI 難以逐段擷取乾淨片段 | 資訊 |

> 後三項「可引用性」是依 Princeton「GEO: Generative Engine Optimization」(KDD 2024) 的內容訊號，只對有一定篇幅的正文頁出題，是軟性建議、不重扣分。

## 5. UX（逐頁）

`scanners.analyze_ux`。量測都在爬取時完成，這裡把量測結果轉成問題。

| 檢查 | 判定標準 | 嚴重度 |
|---|---|---|
| 行動版破版 | 手機寬度下頁面比螢幕寬超過 4px（出現水平捲動）；溢出達螢幕寬一半升為中 | 低／中 |
| 版面跳動（CLS） | 依 Google CLS 定義：>0.1＝低、>0.25＝中；列出移動最多的元素與沒標寬高的圖片 | 低／中 |
| 觸控目標過小 | 手機上可點的按鈕或連結寬或高小於 40px；5 個以上升為中（另註明 WCAG 2.2 的 24px／44px 標準） | 低／中 |
| 表單欄位缺標籤 | input、select、textarea 沒有 label、aria-label、title 或 placeholder | 中 |
| 假按鈕（div／span 當按鈕） | 用 onclick 掛在 `<div>`／`<span>` 上當按鈕、卻沒有 role：螢幕報讀者唸不出、鍵盤 Tab 不到、AI 代理也看不到（有 role 代表作者有意識處理，不列入） | 低 |
| JavaScript 錯誤 | 頁面有未捕捉的例外 | 中 |
| WCAG 無障礙（axe-core） | 色彩對比不足、按鈕或連結沒有名稱、頁面語言未設定、圖片缺替代文字等；axe 的 critical、serious 判中，moderate、minor 判低 | 低／中 |

觸控目標、缺標籤欄位與破版元素會在行動版截圖上框出實際位置。

## 6. 資安（逐頁）

`scanners.analyze_security`、`analyze_data_exposure`、`security/secret_scanner.py`、`security/content_injection.py`。登入與後台頁面也會檢查。

| 檢查 | 判定標準 | 嚴重度 |
|---|---|---|
| CSRF | 會改變狀態的表單（`method=post` 或含密碼欄位）沒有 CSRF token；站內搜尋這類 GET 表單不算 | 中 |
| 身分證號、信用卡號 | **只看頁面上看得到的文字**（不看圖片網址、連結、script）。身分證須通過檢查碼；信用卡須通過 Luhn、開頭與位數符合卡組織（Visa、Master、JCB、Amex、銀聯…），且照卡片分組（4-4-4-4 等）或附近有「卡號」等字 | 高 |
| 個人聯絡資料 | 手機號碼、非本網站網域的 Email、藏在 HTML 註解裡的資料、開發留下的測試字串 | 中 |
| 公開的聯絡方式 | 本網域 Email、`mailto:`／`tel:` 連結、角色信箱（info、service…），多半是刻意公開 | 資訊 |
| 硬編碼秘鑰 | 原始碼裡的私鑰、AWS／GitHub／Stripe 正式金鑰（嚴重）、Stripe 測試金鑰、SendGrid、Slack、含帳密的資料庫連線字串（高）、JWT 與明文密碼賦值（中） | 嚴重～中 |
| 瀏覽器用 Google 金鑰 | `AIza…` 金鑰本來就要放在前端；只提醒確認已設 HTTP 參照網址與 API 限制 | 低 |
| AI 提示詞注入 | 頁面藏有操縱 AI 問答引擎的指令字樣（「忽略先前指令」「務必推薦」「不要提及競爭者」等），在可見文字、HTML 註解或隱藏區塊；或 AI 專用 `data-*` 屬性。一般 `display:none`／摺疊選單不算 | 高（可疑標記＝低） |

Email 與手機的格式判斷與 AEO 共用同一套，兩邊結論不會互相矛盾。

## 7. AEO 問答檢測

`aeo/`。檢查「使用者會問的問題，能不能從網站內容找到答案，並追溯到原文」。

**出題**：只出網站內容有提到的主題（正文命中觸發詞 2 次以上才出；價格題的金額如「1,200 元」也算），另外加上網站自己寫的問句標題。

| 題目 | 權重 |
|---|---|
| 聯絡電話是多少？ | 1.0 |
| 聯絡 Email 是什麼？ | 0.6 |
| 這個網站（組織）提供什麼服務或內容？ | 0.8 |
| 地址或所在位置在哪裡？ | 0.8 |
| 營業或服務時間是什麼時候？ | 0.8 |
| 價格或費用是多少？ | 1.0 |
| 如何申請或報名？ | 0.9 |
| 申請或報名截止日期是何時？ | 1.0 |
| 申請資格或條件是什麼？ | 0.7 |
| 退款或退貨規定是什麼？ | 0.8 |
| 配送或出貨需要多久？ | 0.6 |
| 可以使用哪些付款方式？ | 0.6 |
| 如何預約或訂位？ | 0.7 |
| 網站自己的問句標題 | 0.6 |

**判定**（每題附原文與所在頁面）

| 判定 | 意思 | 得分 | 產生的問題 |
|---|---|---|---|
| 可回答 | 找到具體答案，例如電話號碼、金額、日期 | 100% | 無 |
| 資訊不足 | 有段落談到，但太空泛或缺年份 | 50% | 低 |
| 內容衝突 | 不同頁面寫了不同的價格、時間、截止日或電話 | 25% | 中 |
| 找不到 | 沒有可用答案；權重 ≥1.0 的題目判中 | 0% | 低／中 |

- 不是聯絡方式、也不是網站自己的題目，如果整個網站完全沒談到，就**不計分**（網站可能不提供這項服務）。
- 正文不到 100 字，或可計分的題目少於 3 題時，AEO 標「未充分評估」、不給分。
- 心得、見證段落不能當答案；導覽列、選單連結文字不算；主題詞沒出現的段落不算。
- 另外檢查主要內容是否要執行 JavaScript 才出現（AI 爬蟲多半讀不到），以及答案能否被引用（noindex、nosnippet 會讓答案無法被引用）。
- AEO 分數＝各題權重 × 得分的加權平均，再扣第 3 階段的逐頁問題。

## 站台資安（不顯示）

`scanners.analyze_security_site_level`。伺服器設定整站一致，只檢查一次，不會因頁數多而重複扣分。

| 檢查 | 判定標準 | 嚴重度 |
|---|---|---|
| HTTPS | 頁面用 http | 高 |
| HSTS | 沒有 `Strict-Transport-Security` | 中 |
| CSP | 沒有 `Content-Security-Policy` | 低 |
| 防點擊劫持 | 沒有 `X-Frame-Options`，CSP 也沒有 `frame-ancestors` | 低 |
| X-Content-Type-Options | 沒有 `nosniff` | 資訊 |

## 8. 主動探測

`nuclei_scanner.py`、`katana_scanner.py`。**只在主動模式、使用者勾選授權、且網域已驗證時執行**，被動模式完全不發探測請求。

| 工具 | 範圍 | 做什麼 |
|---|---|---|
| Nuclei | 網站根網址（單頁、全網站都是） | 用固定版本的 CISA「已知被利用漏洞（KEV）」模板，約 500 個模板、600 多個請求；只用中以上嚴重度、排除 DoS 與 fuzz；上限 11 分鐘，逾時保留已找到的結果並標「部分完成」 |
| Katana | 全網站 | 深度探索 JavaScript 裡的 API 端點與技術；用 jsluice 找 JS 檔裡的秘鑰（Google 瀏覽器金鑰降為低） |

兩者共用每秒 2 個請求的上限。目標在 WAF／CDN 之後且 0 項發現時，會註明「結果可能被邊緣過濾、不完整」，不會當成「沒有漏洞」。

## 9. 深度資安

`security/` 子套件。只看首頁與已爬頁面的回應，另外連線讀 TLS 憑證與查 DNS。

| 檢查 | 判定標準 | 嚴重度 |
|---|---|---|
| TLS 憑證到期 | 已過期＝嚴重；7 天內＝高；14 天內＝中；30 天內＝資訊（自動續期屬正常） | 嚴重～資訊 |
| 自簽或憑證鏈不完整 | 瀏覽器會跳警告 | 中 |
| 過時協定 | 還接受 TLS 1.0／1.1 或更舊 | 高 |
| 弱加密套件 | RC4、DES、3DES | 高 |
| Cookie 缺 Secure | HTTPS 網站的 Cookie 沒標 Secure | 中 |
| Cookie 缺 HttpOnly | JavaScript 讀得到 Cookie | 低 |
| SameSite=None 缺 Secure | — | 中 |
| X-Powered-By | 回應標頭洩露後端技術 | 低 |
| 其他資訊標頭 | X-AspNet-Version＝低；X-Generator、X-Recruiting＝資訊 | 低／資訊 |
| CORS | `*` 加上允許憑證＝高；只有 `*`＝中 | 高／中 |
| CSP 品質 | 有 CSP 但含 `unsafe-inline`／`unsafe-eval` | 中 |
| HSTS preload 不符條件 | 標了 preload 但不符瀏覽器預載清單條件 | 資訊 |
| SRI | 跨網站載入的 script、css 沒有 `integrity` | 低 |
| SPF | 沒有 SPF＝中；`+all`（任何人都能冒用寄信）＝高 | 中／高 |
| DMARC | 沒有，或 `p=none` | 低 |
| DNSSEC | 未啟用（最佳實務建議） | 低 |
| 前端套件已知漏洞 | 用 Retire.js 規則比對 jQuery 等函式庫版本；最高判高，另查 EPSS 被利用機率與 OSV 修補版本 | 低～高 |
| 伺服器版本已知漏洞 | `Server`／`X-Powered-By` 的 nginx、Apache、PHP 版本比對 NVD，屬疑似、附驗證方法；最高判高，標頭帶作業系統發行版註記（Ubuntu、Debian、RHEL…）時最高判中。只有版本沒有漏洞＝低 | 低～高 |
| 被 WAF 阻擋 | 掃描時被 403 或驗證頁擋下（代表防護有作用，也代表結果可能不完整） | 資訊 |

注意：伺服器版本是從回應標頭讀的，作業系統套件常會修補舊版本但不改版本號，所以這一項標為「疑似」，報告附上在伺服器上確認修補狀態的方法。

## 13. 連結檢查

`seo/collect.py`、`seo/link_check.py`、`seo/site_findings.py`。

**連結狀態**：收集所有頁面上的連結（依站內→子網域→站外排序，最多 150 個、120 秒），每一跳都記錄。爬取時已造訪過的頁面不重查。

| 結果 | 怎麼算 |
|---|---|
| 正常 | 200，或轉址後 200 |
| 失效 | 4xx（下列除外）、5xx |
| 無法確認 | 401、403、429、999（對方拒絕被檢查）、逾時、連不上 |

**整站網址設定**

| 檢查 | 看什麼 |
|---|---|
| robots.txt | 有沒有；`Disallow: /` 擋住全部搜尋引擎 |
| sitemap | 有沒有、能不能讀 |
| HTTP → HTTPS | http 版本有沒有轉到 https |
| www／非 www | 兩個版本是不是一個轉到另一個 |
| 404 頁面 | 隨機路徑是否真的回 404（不是回 200） |
| `/index.html` 與結尾斜線 | 同一頁有沒有兩個網址 |

**轉成問題的項目**

| 問題 | 嚴重度 |
|---|---|
| 站內連結失效（附來源頁與錨文字，並標新壞掉或持續失效） | 中 |
| 3 頁以上且過半頁面用同一個標題 | 中 |
| 主網址設定不一致（www 與非 www 都直接回應、canonical／og:url／sitemap 指向另一個主機） | 低 |
| sitemap、robots.txt 與 noindex 互相矛盾（sitemap 列出 noindex 或被擋住的網址等） | 低 |

## 15. AI Agent

`apps/agent/`。需要大型語言模型，耗時數分鐘。兩種角色都要平台總開關開啟；**單頁掃描不跑**（沒有流程可走），所以進度條不會出現這個階段。

**擬真使用者 UX 測試**（全網站＋勾 UX，被動模式也跑）

1. 讀取頁面上的互動元素。
2. 找最重要的行動按鈕（立即購買、免費試用、註冊…），點擊並觀察有沒有清楚回饋。
3. 走表單或流程：網域已驗證時可以送出；**未驗證時只填欄位、不送出**，不在別人網站留下資料。
4. 回報按鈕沒反應、流程斷掉、文案看不懂、沒有回饋、找不到返回路徑等問題，附修正方向。

不嘗試繞過驗證、不送出攻擊內容。

AI 回報的 UX 問題最高為中風險（只憑 AI 觀察、沒有規則依據，不應比規則式檢查扣得更重）。token 上限 12 萬（`ARGUS_AGENT_UX_MAX_TOKENS`）；用完時已回報的問題照樣保存，覆蓋紀錄標「部分完成」。

**深度資安測試**（全網站＋主動模式＋網域已驗證）

1. **偵察**：讀取瀏覽器實際發出的 API 請求；對同網站、帶參數的端點驗證 SQL injection；把應該要登入的端點用未登入身分重送，看會不會拿到資料。
2. **派專家**：最多 6 位，依偵察結果決定。

| 專家 | 測什麼 |
|---|---|
| 登入與越權 | 註冊登入流程、讀寫別人的資料（IDOR）、重設密碼接管帳號 |
| 注入 | SQL 注入繞過登入、XSS 實際執行、NoSQL／樣板／XXE／指令／路徑注入 |
| 商業邏輯 | 負數或極端值、跳過流程步驟、驗證碼重用、開放轉址 |
| 資訊洩漏 | 敏感檔案、錯誤頁、除錯端點（只讀） |
| XSS | 反射型、DOM 型、儲存型 |
| JWT | token 內容、竄改簽章或過期時間後重送、Cookie 屬性 |
| 檔案上傳 | 副檔名、檔案類型、路徑、大小限制、上傳後能否被直接讀取 |
| 密碼學 | 偽造 JWT（alg=none、弱密鑰）、可預測的隨機值 |

報告裡 AI Agent 的觀察預設最高顯示為中風險，並標示來源是 AI。**2026-10-10 放寬**：當 Agent 用自己的主動工具（重送請求、注入探測、未授權存取探測、sqlmap）實際重現並確認問題可被利用時，該筆才可顯示為高風險或嚴重（不再需要 Kali sqlmap）；只是觀察、沒實際驗證的仍封頂中風險。

## 16. 彙整評分

`scanners.calculate_scores`。

1. 每個維度從 100 分開始（AEO 從問答檢測的分數開始）。
2. 同一條規則在很多頁出現**只扣一次**，出現在幾頁是影響範圍，不是嚴重程度。
3. 資訊類不扣分。
4. 維度分數＝起始分 × e^(−扣分總和 ÷ 100)，扣分權重見文首表格。這樣分數不會變成 0，也分得出「4 個高風險」和「40 個高風險」。
5. 某個維度的檢查全部失敗或被擋，就標「未評估」，不給分；部分完成照常計分但標「部分評估」。
6. 總分＝有評分的維度平均。
7. 記錄評分公式與規則版本；版本不同的兩次掃描不直接比較分數增減。

最後依實際爬到的頁數結算點數，多扣的退回。

## 17. AI 解讀（掃描完成後，背景執行）

`ai_insight.py`。掃描完成後另外排一個背景任務，不拖慢掃描；平台需開啟 `ARGUS_AI_INSIGHT_ENABLED`。

- **整體診斷**：AI 讀完這次的問題（依規則合併，最多 40 組）與遮罩後的證據，用 3～5 句白話說明網站主要問題與可能原因。
- **建議先處理**：最多 3 件事，每件寫為什麼先做、怎麼做，並對回本次掃描的問題。
- **高風險問題複核**：嚴重與高風險問題（最多 8 項，sqlmap 已實際確認的除外）由 AI 看證據判斷「證據支持／可能是誤報／需要人工確認」。

限制：只送問題標題、說明與遮罩後的證據（個資與金鑰已遮罩），不送頁面原文；AI 的判斷**不改嚴重度、不刪問題、不影響分數**，畫面標明是 AI 產生、僅供參考；PDF 報告不收錄。失敗時可在結果頁重新產生。
