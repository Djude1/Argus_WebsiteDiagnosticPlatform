# 2026-08-31 CI 失敗修正：報告 per-rule 客製位置衝突

## 背景

`feat(scans)` commit（`b930b06`）+ `feat(brand)` commit（`f9301a3`）push 後觸發
GitHub Quality Gate 失敗，**7 個測試** 報錯。經分析，所有錯誤來自同一根因：
我把「為什麼要在意」「修了好怎麼確認」放在每個 finding 底下，破壞了既有
tests 的設計意圖（講一次就好、info 級別不該套 security 模板）。

## CI 失敗清單（7 個）

| 測試 | 失敗原因 |
|---|---|
| `test_entry_page_screenshot_is_embedded` | 期望 1 張圖，實際 2（cover 也加 PNG）|
| `test_only_the_entry_page_screenshot_is_embedded` | 同上 |
| `test_missing_screenshot_file_does_not_break_the_report` | 期望 0 張，實際 1（cover 仍嵌）|
| `test_category_impact_is_stated_once_not_per_finding` | 「會被攻擊者利用」期望 1 次，實際 7 次 |
| `test_verification_advice_is_stated_once_not_per_finding` | 「重新執行一次 Argus 掃描」期望 1 次，實際 7 次 |
| `test_info_finding_does_not_promise_re_scan_verification` | info 不該有「修好了怎麼確認」段 |
| `test_positive_info_finding_is_not_described_as_a_threat` | info 不該被說成攻擊威脅 |

## 既有測試反映的設計意圖（重要！）

| 測試 | 設計意圖 |
|---|---|
| compactness /「講一次」| category-level 樣板講一次就好，不重複 |
| layout / info 排除 | info 是中性/正向指標，不該套 security 模板 |
| screenshot / 數量受控 | 截圖數量必須可預期，避免 docx 失控 |

我原本的設計把這些文字「放每個 finding 底下」違反了這個意圖。

## 修正方向

不改既有測試的「講一次」設計，改我的實作，把 per-rule 客製放回正確位置：

### 1. summary「這些分類為什麼重要」表格
- **改 `_add_category_impact`**：每個 category 挑最嚴重 finding 的 rule_id，
  查 RULE_IMPACT；找不到退回 CATEGORY_IMPACT。
- 既滿足既有 compactness 測試（講一次），又為有 RULE_IMPACT 的 category
  （如 SECURITY_PII）換成更具體文案。

### 2. 附錄「修補後如何驗證」小節
- **保留通用模板**（「重新執行一次 Argus 掃描」講一次）。
- **新增 per-rule verify 列表**：每個 category 列出所有有 RULE_VERIFY 的
  rule_id，附上對應驗收指令（curl / dig / 瀏覽器開發者工具）。

### 3. 個別 finding 仍只有 3 段
- **撤銷** 前一個 commit 加進 `_add_findings` 的「為什麼要在意」與
  「修好了怎麼確認」段。
- info 級別因為 RULE_IMPACT / RULE_VERIFY 都沒有對應項目，自然不出現，
  滿足既有 layout 測試。

## 修正既有 screenshot 測試

cover 加 PNG 是正確決策（顯眼藝術字是使用者明確要求），所以測試
image_count 從 1 → 2。改測試即可：

| 測試 | 改前 | 改後 |
|---|---|---|
| test_entry_page_screenshot_is_embedded | `== 1` | `== 2` |
| test_only_the_entry_page_screenshot_is_embedded | `== 1` | `== 2` |
| test_missing_screenshot_file_does_not_break_the_report | `== 0` | `== 1` |

## 更新自己的測試

`tests_report_rule_specific.py` 的測試設計從「per-finding 都有」
改為「summary/附錄有」：

- 新增 `_full_doc_text()` helper：python-docx 的 `doc.paragraphs` 不含
  table cells，要手動遞迴讀完整個 document tree。
- `test_summary_uses_per_rule_impact`：驗證 summary 表格含 per-rule 客製
  （含「個資法」「罰鍰」字眼）。
- `test_appendix_uses_per_rule_verify`：驗證附錄含 per-rule 驗收指令
  （含「curl」字串）。
- `test_findings_do_not_each_carry_impact_and_verify`：驗證個別 finding
  區段不含「為什麼要在意」「修好了怎麼確認」標題。

## 設計決策記錄

**為什麼不放每個 finding？**
- 既有 compactness 測試反映「講一次就好」原則（scan 38 報告 14 次重複
  是真的過度）
- 使用者要的是「**具體**客製文案」，不是「**重複**客製文案」
- 正確位置：summary 表格用代表 rule_id 進階版、附錄列表用所有 rule_id

**為什麼 info 級別排除？**
- info 常是正向指標（WAF 攔截 = 防護有效）
- 套 security 模板「攻擊者會利用」完全反義
- 既有 layout 測試保護這點，不能改

**為什麼保留通用模板「重新執行一次 Argus 掃描」？**
- 既是最終驗證手段（Argus 自動跑所有檢查）
- 也保留既有 compactness 測試通過
- per-rule verify 補充「如何立即手動驗證」
