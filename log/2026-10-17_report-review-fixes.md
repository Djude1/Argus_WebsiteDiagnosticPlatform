# 審查最新掃描報告後修正：計分順序相依、失效連結漏報、HTTPS 轉址誤扣、API 清單誤收頁面

**日期**：2026-10-17
**操作者**：Claude

## 背景
使用者提供最新一次正式掃描報告（ARGUS-20261017-AE08，實測站台，70 分）要求再次審查。上一輪的兩項修正已生效：API 文件外洩因內網 IP 判為「高」、附錄 API 端點清單列出靜態發現的端點。審查另外發現下列問題，每一項都先在程式碼找到根因才修。

## 變更內容

1. **計分去重與順序相依（`scanners._dedupe_findings_for_scoring`）**
   - 現象：全新掃描的附錄 7.5 卻寫「這次掃描的分數以舊版計分公式算出」，不列扣分明細。SEO 依報告列出的發現重算是 64，保存的是 67。
   - 根因：同一分類同一規則只算一次，但保留的是「第一筆」。掃描當下用記憶體中的順序，事後重算用資料庫的 priority 排序；同一規則在不同頁嚴重度不同（例如某頁 info、某頁 low）時，兩邊挑到不同筆，分數就不同。
   - 修正：改成保留最嚴重的那筆，與順序無關。這是公式變更，`SCORING_VERSION` 3 → 4。
   - 報告文案：扣分明細對不上但計分版本相同時，改說「發現在計分後有被重新判定」，不再誤稱舊版公式。

2. **爬蟲造訪過的 404 頁面沒進「站內連結失效」（`seo/collect.build_link_report`）**
   - 現象：第 1 章失效連結表有 5 個（含 8 頁導覽列都連到的 `/service/1`），發現 4.9 卻說 4 個，漏掉影響最大的那個。
   - 根因：爬蟲已造訪的網址不再做連結檢查（避免重複請求），但它們的狀態碼也沒寫進 `seo_report.links`；報告表格另外從頁面資料補狀態，發現只讀 `links`。
   - 修正：把爬蟲拿到的狀態碼以 `known_result` 寫進 `links`（不多送請求）。

3. **安全標頭等第「HTTP 轉址到 HTTPS」一律被扣 20 分（`security/observatory._redirection`）**
   - 現象：同一份報告「網站優勢」說 HTTP 會自動轉到 HTTPS，「安全標頭等第」卻扣 -20。
   - 根因：讀站台檢查的 `verdict` 欄位，但 SEO 站台檢查產生的欄位是 `level`，永遠讀不到「pass」。有勾 SEO 的每個網站都被誤扣（信任輪廓的技術信任也跟著偏低）。測試 fixture 同樣寫成 `verdict`，所以一直綠燈。
   - 修正：改讀 `level`；測試 fixture 改成真實欄位，另加一個用 `link_check._site_check` 產生真實格式的契約測試。

4. **API 端點清單把一般頁面當 API（`tasks._static_api_paths`）**
   - 現象：清單列出 `/service/1`（其實是導覽列連到的頁面）。
   - 根因：JS 路徑的 API 提示字含 `service`，頁面網址也會命中。
   - 修正：靜態抽出的路徑排除爬蟲當網頁造訪過的路徑；API 清單與 API 前綴推導（敏感檔案探測）都套用。

5. **API 文件外洩卡片的判定依據自相矛盾、內網 IP 證據被截掉（`security/exposure_scanner`）**
   - 現象：類型寫「已驗證弱點」，判定依據卻寫「規則或範本比對的結果未經人工重現」；描述有內網 IP，但檢測依據沒有判讀內容；修法沒提到要移除規格裡的內網位址。
   - 根因：高風險沒有 `assessment` 時套用通用預設文字；報告檢測依據只取前 300 字，內網位址判讀排在 400 字內容片段之後。
   - 修正：證據順序改為命中→內網位址→秘鑰→個資→內容片段；每筆附 `evidence_json.assessment`（主動探測已實際取得檔案，未驗證的是 API 是否缺授權、內網位址能否從外部連線）；API 文件的修法加上關閉 springdoc／springfox、移除 Swagger 2.0 `host`／OpenAPI 3 `servers` 的內網位址。

6. **規則集版本**：上一輪改了嚴重度規則卻沿用 `2026.10.16`，所以這份報告把 73 → 70 當成網站變差（-3 分其實是規則改變）。`RULESET_VERSION` 改為 `2026.10.17`，之後的掃描與舊掃描比較會顯示「評分規則已更新」。

7. **安全：移除站名與真實漏洞路徑的對應**：先前的程式註解、測試與 log 把實測站台名稱和它尚未修補的 API 文件路徑寫在一起，違反「修補前不寫進 repo」的約定。目前版本改用「實測站台」、`site.example` 與 `<代理前綴>`；程式行為不變。**已推上去的歷史 commit 仍含這些字串**，要不要清歷史由使用者決定（需要改寫已推送的分支歷史）。真實內網 IP 從未寫進 repo。

## 影響範圍
- 計分版本 4：新掃描與計分版本 3 的舊掃描不可直接比較（前端與報告會顯示「評分規則已更新」）。同規則跨頁嚴重度不同的網站，分數可能略降（以最嚴重的那頁計）。
- 失效連結：爬蟲造訪時回 4xx 的頁面現在會算進「站內連結失效」；趨勢比較第一次會把它們標成「新壞掉」。
- 安全標頭等第：有 HTTP→HTTPS 轉址的網站加回 20 分；已完成掃描保存的等第不會自動改變，重新掃描後才更新。
- 不新增 model／migration（0035 只改說明文字，不改 operations 與 dependencies）。

## 驗證方式
- 後端：`ruff check backend` 通過；`manage.py check` 無問題；`makemigrations --check` 無變更；後端全套 1963 項通過（skipped 12）；去除站名後 `apps.agent`＋`apps.scans` 1471 項再跑一次通過；根目錄 `tests/` 36 項通過（`kubectl` 需在 PATH 上）。
- 新增測試：計分取最嚴重且與順序無關；同版本對不上的說明文字；爬蟲 404 頁面進失效連結與發現；靜態 API 路徑排除已造訪頁面；HTTPS 轉址的真實格式契約；API 文件證據順序、判定依據與修法。
- 無法在本容器驗證：對實測站台重掃（容器出口 TLS 被代理重簽，且不應從這裡對第三方網站送主動流量）。待正式環境重掃確認：附錄 7.5 列出扣分明細、4.9 含 `/service/1`、安全標頭等第不再扣 HTTPS 轉址分、API 清單不含 `/service/1`、4.1 檢測依據可見內網位址判讀。
