# 修正：migration 0019 遇到殘留的網站專案表時失敗

**日期**：2026-10-02  
**操作者**：Claude

## 變更內容
- `backend/apps/scans/migrations/0019_site_projects.py`：最前面新增 `drop_orphaned_site_project_schema`。0019 尚未套用、但資料庫已有 `scans_siteproject` 表或 `scans_scanjob.project_id` 欄位時，先移除它們再建立（PostgreSQL 以 `DROP COLUMN ... CASCADE`／`DROP TABLE ... CASCADE`；SQLite 先刪欄位索引再 `DROP COLUMN`），之後照常依既有掃描回填專案。
- `backend/apps/scans/tests_site_projects.py`：新增 `SiteProjectMigrationRecoveryTests`（停在 0018、造出殘留表＋欄位＋索引，再套用 0019，確認成功且掃描全部歸入專案）。
- `backend/apps/scans/CLAUDE.md`：記錄這個行為與「回退含 migration 的功能要反向 migrate」。

## 原因
使用者以 Docker Compose 部署時 `migrate` 失敗：

```
Applying scans.0018_scanjob_aeo_report... OK
django.db.utils.ProgrammingError: relation "scans_siteproject" already exists
```

資料庫的 migration 紀錄停在 scans 0017，卻已有 `scans_siteproject`。這張表只有 0019（網站專案）會建立，代表先前被回退的網站專案版本曾在這個資料庫跑過，回退時程式與 migration 紀錄退回了，表卻留著。

## 影響範圍
- 只影響「0019 尚未套用」的資料庫；已套用 0019 的資料庫不會再執行這段。
- 殘留表裡的專案資料（名稱、封存狀態）會被捨棄，由回填依既有掃描重建（名稱回到網域名稱）；掃描、finding、點數紀錄不受影響。

## 驗證方式
- 本機 PostgreSQL 16 重現使用者狀態（紀錄停在 0017、無 MCP 表、殘留第一版 `scans_siteproject` 與 `project_id`），修正前出現相同錯誤，修正後依序套用 mcp_access 0001、scans 0018、0019 成功，兩個網站的專案回填、未歸入掃描 0 筆。
- 另驗證：只殘留表、全新資料庫、已是最新（不動作）、SQLite 殘留表＋欄位，皆通過。
- `SiteProjectMigrationRecoveryTests` 在 SQLite 與 PostgreSQL 皆通過；暫時拿掉修正時該測試以相同的 `DuplicateTable` 失敗。
- `manage.py test apps` 全數通過、`ruff check backend` 通過、`makemigrations --check` 無變更。
