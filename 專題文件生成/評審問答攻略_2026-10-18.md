## 〇、初審三位委員意見的逐點回應（複賽最可能追問，優先熟記）

> 複賽委員常先問「初審被提的點改了沒」。以下照初審意見逐條，給「已做到什麼／怎麼回應」。
> 誠實原則：做得到的講清楚、範疇外的畫清邊界，不含糊。

### 委員 1（偏重：看得到的實例與修復清單）
- **1-1 把弱點列表說明**：在「問題分析」頁依規則合併同次掃描結果，逐列顯示嚴重度、問題標題與說明、
  分類、受影響頁數、修正重點、連續出現次數、與前次的變化；資安問題另標四種類型（設定建議／曝露面／
  疑似弱點／已驗證弱點）。可依維度、嚴重度、文字篩選，並匯出 CSV。答辯時直接開這一頁逐欄講。
- **1-2 用簡化實例實際演示修復清單**：用內建示範專案「晨光咖啡烘焙所」（虛構網站的真實掃描）或對一個
  小網站現場掃，展示「問題 → 查看詳情（原始證據、截圖框住實際元素位置、怎麼修、可複製『給 AI 的
  提示詞』）→（可選）網頁優化前後對照」。**建議準備一個 3～5 頁的自備小站當 demo 實例**，流程最短、最穩。

### 委員 2（偏重：合法授權、涵蓋範疇、定期更新、落地 PoC、答辯分工）
- **2-1 答辯由每位成員分別回覆**：這是對團隊的提醒，非系統功能。回應：已分工，開場各自報負責模組
  （建議：組長定位與商模、A 掃描方法與準確度、B AI Agent 與資安、C 架構與維運），問答時由對應負責人主答。
- **2-2 網域所有權識別、參考 TWCA 驗證機制**：已實作四種「擁有權證明」且主動掃描必過其一：
  Search Console（siteOwner）、DNS TXT（`_argus-verification.<網域>`）、首頁 meta 標籤、
  `/.well-known/argus-verification.txt` 驗證檔。與 TWCA「以控制 DNS／網站檔案證明網域控制權」的精神一致
  （我們不簽發憑證，但用同類擁有權證明當掃描授權閘）。主動模式未通過驗證一律擋下。
- **2-3 涵蓋範疇（靜態原始碼／主機／Web 應用／滲透）＋定期更新 OWASP**：誠實定位 Argus 為
  **「已授權的黑箱 Web 應用檢測＋AI 滲透」**，並畫清邊界：
  - **做**：Web 應用被動＋主動（Nuclei 已知漏洞 KEV 模板、敏感檔探測、未授權／IDOR 探測、OWASP ZAP
    被動／主動）＋AI Agent 推理型滲透（越權、業務邏輯），對映 OWASP Top 10:2025 與 CWE。
  - **不做（刻意）**：靜態原始碼掃描（SAST，需源碼、我們是黑箱）、主機層 Port／服務弱點掃描（需掃對方
    主機、授權面與風險面不同）。把「範疇邊界清楚、責任明確」當成強項，而非缺點。
  - **定期更新機制**：每月 GitHub workflow 自動比對 Nuclei 引擎／模板是否有新版並開 issue 提醒維護者；
    OWASP 已對照 2025 版、每筆附 CWE，並向 EPSS（被利用機率）、OSV（修補版本）查詢補強。
- **2-4 與校內單位／系所合作做校園網站資安健檢 PoC**：非常契合——Argus 的「網域驗證＋主動授權」閘天然
  適用校內網站（由 IT 或系所證明擁有權即可授權掃描）。回應：願意規劃一次校內 PoC，範圍、速率與稽核可控。

### 委員 3（偏重：量化商模、所有權確認、文件完整、全面紀錄、金流與管理、後端 API）
- **3-1 商業模式成本與收益量化**：成本面——開源技術棧無授權費，主要變動成本是雲端資源、LLM token、
  PageSpeed Insights 與金流手續費；每次掃描的單位成本可由「頁數×維度＋是否跑 Agent」估。收益面——
  點數包（一次購買）＋月訂閱（固定點數＋MCP）。後台「方案與定價」頁有每頁 coin 與成本／毛利試算
  （`planEconomics`）。**建議在簡報放一張單位經濟表：每次掃描成本 vs 點數定價 vs 毛利**。
- **3-2 如何確認被掃描網站為使用者所有**：同 2-2 的四種網域所有權驗證；主動掃描必過，未驗證只能被動
  讀公開回應。並保存授權聲明與驗證紀錄。
- **3-3 第 5、6、7 章（需求／設計／實作模型）過於精略，重新寫完整**：承認並承諾補完整——使用個案描述、
  循序圖、設計類別圖、部署／套件／元件圖、狀態機。**這是文件工作，我可協助依現行程式產生這三章的完整
  內容**（已有狀態機與部署事實可據）。
- **3-4 強化使用者所有活動紀錄蒐集**：已有 LoginEvent（登入方式／IP／UA）、AdminAuditLog（管理操作稽核、
  不可刪）、每次掃描 scan_log、CoinTransaction 帳本（不可改）。回應：可再補「一般使用者端關鍵操作紀錄」
  （建立／取消掃描、購點、網域驗證、分享）集中檢視。
- **3-5 補上訂閱、扣點及收費功能**：已完整實作——點數錢包、預扣（scan_hold）／依實際頁數結算／退款、
  綠界一次購點與定期定額訂閱、月贈點、後台訂單與每期扣款對帳。文件見 12-10 與第 8 章帳務資料表。
- **3-6 補上系統管理員維護功能**：React 後台 `/admin/*`——概覽、掃描任務（取消／重排）、使用者（調點／
  停用／刪除／授權）、網域人工審核、訂單、點數交易、評論治理、內容 CMS、公告、系統健康、操作日誌。
- **3-7 能否對後端程式或 API 進行檢測**：黑箱可做「對外可觀測的 API 面」——被動 API 檢查（前端呼叫的
  同站 API：錯誤堆疊洩漏、CORS 任意來源）、未授權／IDOR 探測、Katana 從 JS 靜態抽出 API 端點、API 文件
  探測（Swagger／`v3/api-docs`）、AI Agent 重送帶參數請求驗 SQL 注入與越權。**不讀後端原始碼**（無源碼，
  屬 SAST 範疇）。結論：API 的「對外行為」查得到，原始碼層不在範疇。

## 一、定位與問題（為什麼要做）

**Q1. 市面上 SEO／資安工具很多，Argus 的差異是什麼？**
一般工具多半只做一件事、各給一個分數，且不告訴你「問題在哪一頁的哪個位置、該先修哪一個」。Argus 把
SEO、AEO、GEO、UX、資安五個面向整合成一條可從頭追到尾的流程：授權 → 爬取 → 蒐證 → 計分 → 排優先序
→ 報告，每個問題都附截圖位置、原始片段與具體修法，照排好的順序修就好。採點數制而非高額月費，門檻低。

**Q2. 什麼是 AEO、GEO？為什麼要做這兩個？**
AEO（Answer Engine Optimization）檢查「使用者會問的問題，能不能從你網站內容找到答案並追溯原文」，
因應搜尋結果頁與 AI 助手直接給答案、不再點進網站的趨勢。GEO（Generative Engine Optimization）檢查內容
是否容易被生成式 AI 理解與引用（結構化資料、可引用段落、權威來源、量化數據等，依 Princeton KDD 2024
的訊號）。兩者是傳統 SEO 沒覆蓋、但對「被 AI 看見」越來越關鍵的面向。

**Q3. 目標客群是誰？**
個人品牌經營者、新創團隊、中小企業——「偶爾掃描、需要時修正」，負擔不起也不需要高額企業月費的族群。

## 二、技術架構

**Q4. 整體技術棧與資料流？**
後端 Django + DRF、前端 React、爬蟲與 Agent 用 Playwright（真實 Chromium）、背景任務 Celery、資料庫
PostgreSQL、佇列與快取 Redis；正式環境 K8s + Argo CD（GitOps）＋ cloudflared 對外。資料流：使用者填網址
→ `POST /api/scans/`（billing 預扣點數）→ Celery worker 跑爬蟲與五維 scanner →（可選）AI Agent → 結果寫 DB
→ 前端輪詢取結果 → 產 PDF 報告。

**Q5. 為什麼用真實瀏覽器爬取，而不是純 HTTP？**
很多網站內容與版面要執行 JavaScript、等渲染後才正確；UX 的版面位移（CLS）、觸控目標、破版、無障礙
（axe-core）都需要真實排版才量得到。所有耗時工作（開頁、等渲染、截圖、行動版量測）在爬取階段每頁做
一次，後續五個逐頁分析階段只拿結果比對規則，所以通常只需數秒。

**Q6. 系統怎麼確保穩定、可重現？**
每次掃描記錄「判定規則版本」與「計分公式版本」，版本不同的兩次掃描不直接比較分數；外部工具版本
（瀏覽器、axe-core、Nuclei、Lighthouse）也記錄。並有「掃描覆蓋契約」逐項記錄每個檢查是否完整跑完，
工具失敗不會被呈現成「0 項問題」。

## 三、掃描方法與準確度（最可能被深究）

**Q7. 你怎麼證明判定是準的，不是隨便給分？**
兩個面向有人工標註的回歸資料集並設不參與調規則的保留集：AEO 問答檢測與網站特徵辨識，要求精確率／
召回率／準確率 ≥ 95%、誤判率 ≤ 5%，門檻納入自動化測試，改規則只要任一指標未達標測試就失敗。其餘
規則式檢查以單元測試鎖定具體案例（已知輸入 → 預期判定）。

**Q8. 誤報（false positive）怎麼控制？舉例。**
刻意保守、寧可漏不可誤。例：未授權 API 外洩要先是「成批記錄」再滿足身分＋內部帳號欄位／敏感欄位名／
強個資任一才報，公開商品清單、人員目錄排除；信用卡號要過 Luhn、身分證要過檢查碼；SRI 排除官方不提供
雜湊的服務（GA、Stripe…）；密碼欄位 `type=text` 但值是程式運算式（`document.getElementById`）不算硬編碼
秘鑰。每一刀都附「證據／成立條件／尚缺證據／驗證方法」。

**Q9. 漏報（false negative）呢？會不會讓使用者誤以為安全？**
三道防線：(1) 覆蓋契約——某維度檢查全失敗或被擋時標「未評估」而非 0 問題；(2) 一頁都抓不到時整個掃描
標失敗並全額退點、不給看似正常的分數；(3) 主動掃描 0 發現且目標在 WAF／CDN 之後時，報告明講「結果
可能不完整、不等於沒有漏洞」。歷史比較的「已修好」也要正向重探確認（回 401/403/404）才算，不靠
「這次沒出現」推斷。

**Q10. AEO 問答檢測具體怎麼運作？**
依網站內容實際談到的主題出題（正文命中觸發詞 2 次以上）＋網站自己寫的問句標題，逐題在已爬頁面找答案
並附原文、所在頁面與段落；分四層：能否取得內容 → 能否找到答案 → 答案是否可用（空泛、沒年份、互相
矛盾）→ 標記是否與頁面一致。可回答／資訊不足／內容衝突／無答案給不同權重；內容不足以出題標「未充分
評估」不給分，避免沒做問答卻顯示滿分。

**Q11. 分數怎麼算？為什麼用指數衰減？**
每維度從 100 起算（AEO 從問答基準分起算），同一條規則多頁只扣一次，info 不扣分，維度分數＝起始分 ×
e^(−扣分總和÷100)。線性扣減會讓 4 個與 40 個高風險看起來一樣、也會把只缺幾個 header 的網站判成 0 分；
指數衰減在整個區間都保有解析度、不會歸零。整體分數＝有評估的維度平均，未評估維度不列入分母。

## 四、AI Agent（最可能被挑戰「噱頭還是真功夫」）

**Q12. AI Agent 到底做什麼？和規則式掃描差在哪？**
兩層設計：**確定性層**（規則、Nuclei、ZAP、敏感檔／未授權探測）每次穩定可重現；**AI Agent 層**像滲透
測試員實際操作網站，找「需要推理與串接」才找得到的弱點（越權存取、業務邏輯、帳號接管）——這些規則
難以窮舉。兩種角色：擬真使用者 UX 測試、深度資安滲透。

**Q13. AI 會不會亂報、把臆測當漏洞？**
會嚴格把關。AI 回報的資安觀察預設最高只到中風險，且必須「以自己的主動工具實際重現過該端點」並帶
`verified=true` 才保留高／嚴重；證據必填、經遮罩；描述固定標明「AI Agent 觀察」與成立條件、尚缺證據、
驗證方法。未經工具驗證的 AI 觀察不會排在第一優先。

**Q14.（接 Q13 關鍵）AI 那麼不確定，會不會讓分數每次不一樣？**
正是我們這版（ADR-0006）處理的重點：**AI Agent 的資安觀察不計入可比較的基準分**，headline／各維度／
整體分數只由確定性層計算，同站同碼每次一致；AI 的發現另列為「AI 深度測試」摘要獨立呈現。這樣「看趨勢」
誠實、又不埋沒 AI 的深度發現。Kali 等以工具實際確認的漏洞仍計入分數。

**Q15. AI Agent 一定會跑嗎？成本怎麼控制？**
預設關閉（平台總開關），且深度資安 Agent 是**使用者加購的付費選項**（勾選才跑、才加收點數，實際執行
才收、沒執行退回）；沒勾時只跑確定性層與擬真使用者 UX 測試。每個子代理有步數與 token 上限、派工上限，
用完就收尾並標「部分完成」。

**Q16. 怎麼防止 AI Agent 變成攻擊工具、打到別人網站？**
三層閘：工具清單隔離、執行時再確認模式、只允許與受測網站同源，跨網站一律拒絕；沒有可任意前往其他
網址的工具；重送請求禁止刪除類方法、不跟隨轉址；網域未驗證時不送出任何表單。知識庫是離線通用方法論
（不含特定網站內容、查詢不連外）。而且要先通過網域所有權驗證＋主動授權才會開放這些工具。

**Q17. 用哪個模型？換模型會怎樣？**
MiniMax-M3 為主，GLM、Gemini 為 fallback 服務鏈（前一家失敗自動換）。架構與工具是模型無關的；換更強
模型時「工具採用率」是第一個觀測點。我們誠實記錄了目前模型的已知限制（例如某些條件工具採用不足）。

## 五、資安、隱私與合規

**Q18. 你們會對別人網站發動掃描，法律與授權怎麼處理？**
「先授權、再掃描」。被動模式只讀公開回應；**主動模式**（Nuclei、敏感檔探測、深度資安 Agent）必須同時
主動模式＋使用者勾選授權＋通過網域所有權驗證（Search Console／DNS TXT／meta／驗證檔）才執行，並全程
稽核。送出掃描即聲明擁有或已獲授權，系統保存授權紀錄。

**Q19. 會不會被拿來打內網（SSRF）？**
入口網址正規化、DNS 解析檢查、阻擋 localhost／內網 IP／雲端 metadata IP／非 80/443 埠；redirect 後再驗、
scheme allowlist、受限 egress；主動探測逐請求 `max_redirects=0` 防 open-redirect 被導去 metadata。

**Q20. 蒐集到的個資與秘鑰怎麼處理？**
報告與問題不主動收錄密碼／Token／Cookie 值／表單敏感內容；寫入 DB 與 log 前先遞迴遮罩網址查詢字串、
錨點與個資欄位。個資分級：身分證／信用卡才高風險，手機／非本站 Email／註解內資料為中，本站公開聯絡
方式只提示。對外查驗端點只揭露報告編號、目標、時間與分數，不揭露掃描發起人。

**Q21. Kali／sqlmap 這種攻擊工具呢？**
SQL 注入主動驗證（Kali sqlmap）程式已完成並有 Docker／K8s 整合，但**正式環境維持停用**（雙重 disabled：
設定開關＋Admission 政策）；啟用需走 runbook 做靜態加密、RBAC／Admission／Network 實機檢查與授權
positive test。這是責任邊界的刻意保守。

## 六、商業模式與計費

**Q22. 怎麼收費？**
點數制為主、月訂閱為輔。預估點數＝頁數上限 × 選取維度數 × 每維單價（倉庫預設每頁每維 2 點）＋符合條件
的 Agent 附加費（UX Agent 20 點、深度資安 Agent 50 點，後者加購才收）。新帳號享一次免費完整掃描、每月
免費贈點；失敗或取消全額退點。正式金流走綠界（一次購點＋定期定額訂閱）。

**Q23. 點數扣款會不會重複扣或扣錯？**
所有錢包寫入經單一計費服務，用 `transaction.atomic` ＋資料列鎖，預扣（scan_hold）→ 依實際頁數結算
（多扣退回 scan_refund）；交易帳本不可改，補正用 admin_adjust。深度 Agent 費「實際執行才收、沒執行退回」。

**Q24. 這個商業模式能獲利／可行嗎？**
開源技術棧無授權費、成本低；點數制讓使用者按需付費、降低門檻；後台有成本／毛利試算（每頁 coin 數來自
後端設定）。定位是低門檻工具型 SaaS，不與企業級高價產品正面競爭。

## 七、可信度、報告與追溯

**Q25. 報告可信嗎？會不會被竄改？**
報告為 PDF，提供公開「報告查驗」：輸入報告編號可核對目標、時間與 PDF 的 SHA-256 指紋；另存或編輯 PDF
後指紋會變，需保留原始交付檔。編號存在只代表有紀錄，指紋相符才代表內容是發出的版本。

**Q26. 同一次掃描的「114 項」和專案的「21 個問題」為什麼對不上？**
統計單位不同：原始 Finding 筆數（同規則跨 5 頁算 5 筆）、依規則合併的「問題」數（算 1 個）、受影響頁數。
報告與問題分析各自標明欄位語意，不是矛盾。

**Q27. 「做得好的地方」會不會和問題自相矛盾？**
不會。網站優勢每項附依據與可信度（直接量到為「確認」、間接推論標「推論」），且不與同次發現的問題
矛盾；偵測到 CDN 不等於 WAF 有攔截，只有掃描請求實際被擋（403／驗證頁）才寫「防護已生效」。

## 八、限制與誠實邊界（評審常用來測團隊成熟度）

**Q28. 你們最大的限制是什麼？**
誠實講三點：(1) 黑箱掃描看不到後端原始碼，未發現不等於沒有隱藏 API 或業務權限問題；(2) AI Agent 是
非確定性的，深度發現的有無會變動，所以我們把它排除在可比較基準分之外；(3) 版本比對的 CVE 屬「疑似」
（標頭版本可能被發行版 backport 修補），附確認方法而非直接斷定。

**Q29. 外部指標（Lighthouse、CrUX、Observatory、EPSS）為什麼不併入分數？**
它們是第三方或單次量測、口徑與 Argus 不同（Lighthouse 只看首頁基本項目、Argus 檢查全部掃描頁），併入
會誤導。所以獨立呈現並註明不計入 Argus 分數、非官方結果。

**Q30. 如果網站在 Cloudflare／WAF 後面，掃描還準嗎？**
會辨識掃到的是 CDN／WAF／反向代理邊緣還是主機，並在結果與報告提醒「部分 Port／服務／主機層資訊
可能受架構影響」；主動掃描被擋時標「結果可能不完整」，不當成「沒有漏洞」。

## 九、工程與維運

**Q31. 怎麼部署？掛掉怎麼辦？**
Docker Compose（本機／demo）與 K8s + Argo CD（正式，GitOps 自動同步）。push 不等於部署完成，需分別檢查
Quality Gate、image build、bot 回寫、Argo Sync/Health、migrate PreSync Job 與 Pod rollout。後台「系統健康」
以掃描鏈路圖（DB→Redis→Worker→佇列→掃描）顯示斷點。

**Q32. 測試覆蓋如何？**
後端數百項單元／整合測試（`manage.py test apps`），前端 ESLint＋TypeScript typecheck＋Vitest，三者都在
CI Quality Gate 跑、任一失敗前端 image 不會建出。API 型別由後端 schema 自動產生、禁止手改，避免前後端
靜默失效。準確度回歸集見第 10 章。

**Q33. MCP 接入是什麼？**
讓使用者在 Claude Code／Codex／Cursor 等用自己的憑證直接呼叫 Argus 的掃描工具（Streamable HTTP），受
訂閱權益與額度控制，建立掃描仍另預扣點數。體現「可被 AI 工具串接」的定位。

## 十、團隊可能被追問的「刁鑽題」

**Q34. 你們這不就是把現成工具包一包？創新在哪？**
整合不是堆疊：五維共用同一條爬取與證據管線、同一套覆蓋契約與版本治理；AEO／GEO 的可回答性與生成式
引用訊號是自研判定（有回歸集把關）；兩層（確定性＋AI）分數分離、AI 觀察正向重探才判已修好，是我們對
「AI 掃描不可重現」這個業界痛點的具體解法。

**Q35. AI Agent 找到的東西，確定性工具找不到嗎？能否舉例？**
確定性補位是我們持續在做的事：把 Agent 偶然打到的「未授權成批個資 API」沉澱成每次都跑得到的
確定性 BOLA／IDOR 探測。真正留給 Agent 的是需要登入態串接、跨步驟推理的業務邏輯與越權，這些規則
難窮舉。

**Q36. 分數會不會因為你們改規則就變來變去，讓使用者無所適從？**
所以才有版本治理：改規則就升規則版本、改公式就升計分版本，版本不同不給直接比較分數的箭頭；歷史比較
的「新增／持續／已修好」以跨掃描正典身分（正規化端點＋弱點類別＋OWASP/CWE）判定，不被措辭漂移影響。

**Q37. 為什麼第一次免費？不怕被濫用？**
降低新使用者體驗完整流程的門檻；免費僅限被動、全網站、五維的標準掃描，失敗或取消不算用掉，和公開
單頁快速檢查是不同東西。主動掃描與深度 Agent 仍要授權與付費，濫用面有限。

**Q38. 如果現場 demo 掃描卡住或失敗怎麼辦？**
我們有覆蓋契約與明確狀態機：卡 queued 檢查 broker／worker；一頁都抓不到會標失敗並全額退點。demo 時
會用已完成的掃描報告與示範專案（晨光咖啡，虛構網站的真實掃描）確保有東西可展示，不依賴現場即時掃完。

## 十二、現場 demo 畫面會被問的題（信任輪廓、GEO、搜尋關鍵字）

> 這一節對應「架構與信任」頁與「SEO 分析 → 搜尋關鍵字」頁實際會出現的畫面，數字以 demo 當天為準。

**Q39. 為什麼沒有單獨的 GEO 分析頁面？**
GEO 不是沒做，是刻意不另開分頁：它的輸出型態和 SEO／資安不同。SEO 有逐頁清單、連結狀態、關鍵字；
資安有標頭等第、問題類型；GEO 的檢查（組織實體與 sameAs、文章作者與日期、可引用性、RAG 分塊、內容衰退、
AI 爬蟲政策、llms.txt）幾乎都是**軟訊號**（低／資訊等級，刻意不重扣分），單獨成頁會變成一頁「沒什麼要修」
的空清單。所以 GEO 分成三處呈現：(1) 總覽的五維分數有 GEO 一格；(2) 問題分析把 GEO 的資訊級訊號獨立成
「軟性建議」區，與要處理的問題分開；(3) 掃描詳情的「架構與信任」頁把 GEO 的站台層訊號聚合成「信任輪廓」
與「AI 爬蟲政策」。評審若追問「那 GEO 到底檢查了什麼」，回答：依 Princeton KDD 2024 的 GEO 研究，加入
權威來源、量化數據、引言可分別提升被生成式引擎引用的機率約 27%／33%／41%，Argus 就是檢查這三類訊號
有沒有出現，再加上實體／作者／日期／可摘要結構。

**Q40. 信任輪廓五層是什麼？怎麼解讀分數？評分依據是什麼？**
它是「把這次掃描**已經算出來**的訊號，換成 AI 與搜尋引擎眼中的可信度」來看，不重新偵測、不發請求、也
**不計入 Argus 分數**（純參考）。五層與依據：

| 層 | 看什麼 | 來源與扣分（100 起算，命中即扣、下限 0） |
|---|---|---|
| 技術信任 | HTTPS／安全標頭 | 直接取安全標頭參考等第（依 Mozilla HTTP Observatory 公開規則離線計算）的分數；勾資安才評 |
| 身分信任 | 網站是誰 | 缺組織結構化資料 −40、文章缺作者 −30 |
| 社群信任 | 外界怎麼指認你 | 結構化資料沒有 sameAs（連到維基百科／Wikidata／社群）−40 |
| 學術信任 | 說法有沒有憑據 | 正文無權威來源引用 −45、幾乎沒有具體數據 −25 |
| 一致性信任 | 訊號會不會自相矛盾 | 文章缺日期 −25、日期無效 −20、JSON-LD 與 meta 日期不一致 −20、內容衰退 −20、索引指示矛盾 −20、多頁同標題 −20 |

後四層只在有勾 GEO 時評分；沒勾到的層顯示「未評估」且不進分母。**總分＝已評估各層的平均**，等第
A ≥90、B ≥80、C ≥70、D ≥60、其餘 F。以 demo 畫面為例：技術 35、身分 100、社群 100、學術 100、一致性
100 → (35+100+100+100+100)÷5 = 87 → B。解讀方式是看「哪一層拖低」：這個例子四層內容面都滿分，只有技術
信任 35，代表問題集中在伺服器回應標頭（HSTS／CSP／X-Frame-Options 等），對應的修法在資安分析頁已逐項
列出；修好標頭後重掃，技術層上升、總分就跟著上去。若評審問「為什麼內容層都 100」：代表這次掃描沒有命中
任何一條對應規則（例如網站有組織 JSON-LD、有 sameAs、文章有引用與數據），不是沒檢查——層內「reasons」
為空就是滿分。誠實邊界：這是規則式聚合，不是對 AI 模型實際行為的量測。

**Q41. 搜尋關鍵字表怎麼解讀？這些搜尋詞是怎麼出現在排名上的？**
資料來源是使用者授權連接的 Google Search Console（唯讀 scope），Argus 不自己猜排名。表中每一列是一個
「使用者在 Google 實際輸入的搜尋詞」，Google 回報期間內（7／28／90 天，資料延遲 2 天）：曝光＝網站在
該搜尋結果頁出現幾次、點擊＝其中被點進來幾次、CTR＝點擊÷曝光、平均排名＝每次曝光時的名次平均、對應
頁面＝Google 帶訪客去的那一頁（同一搜尋詞取點擊最多、再曝光最多的頁）。所以「怎麼出現在排名上」的答案
是：Google 判斷你的某一頁與該搜尋詞相關就會展示，這張表是展示紀錄的統計，不是某一刻的即時名次（頁面
下方的說明文字也這樣寫）。

幾個典型型態可以現場指給評審看：
- **品牌字**（例如網站簡稱）：曝光少、CTR 高、排名 1–2 → 找你的人找得到，這是健康的。
- **機構大字**（例如校名縮寫）：曝光數千、CTR 不到 1%、排名 8 左右 → 搜的人多半不是找你，但你出現在
  第一頁尾端；要不要經營看這個字是否值得。
- **課程／服務名**：曝光幾十、CTR 5%、排名 4–5 → 這是最值得優化的字：第一頁、有意圖、但標題與描述
  可以更吸引人以拉高 CTR。
- **搜尋到 PDF 檔或子網域的字**（例如某份簡報被英文長尾字搜到、排名 50–90）：代表 Google 收錄了附件，
  但那不是你的主要內容；可判斷要不要為這個主題做一頁正式內容，或用 noindex 把附件收掉。
- **人名**：成員頁被用人名搜到，CTR 差異大；屬於正常現象，不需特別優化。

**Q42. 根據這些數據可以做什麼優化？**
Argus 不只列表，會把目標關鍵字和這些搜尋詞交叉比對（`落差分析`）：
1. **最佳排名分段**：第 1 頁（≤10）維持；第 2 頁（11–20）最有機會推進，建議加強相關頁面的標題與
   內容；20 名以後建議建立或加強以該主題為主的頁面。
2. **落地頁不一致**：Google 帶訪客去的頁面，和 Argus 依內容判定最相關的頁面不同時提示——確認哪一頁才是
   該主題的主頁，並從其他頁面連結過去。
3. **有提到但沒曝光**：頁面有關鍵字卻沒有搜尋曝光 → 先確認已收錄（頁面可用網址檢查 API 逐頁查），再把
   關鍵字放進 Title 與 H1。
4. **高曝光低 CTR**：改標題與 description（SEO 頁面分頁會列出 Title／Description 長度與重複問題）。
這些建議都來自公式與頁面證據，不是 AI 生成的泛泛建議。

**Q43. 「有曝光但還不是目標的搜尋詞」是什麼意思？設成目標關鍵字會有什麼效果？**
意思是：Google 已經因為這些字把你的網站展示給使用者（曝光 > 0），但它們不在你設定的目標關鍵字裡
（字面上既不包含任何目標字、也不被目標字包含），依曝光排序列前 10 個。這是「市場告訴你的機會」：你沒
打算經營、但已經有人這樣搜到你。

設成目標關鍵字**不會改變 Google 排名**——Argus 是診斷工具，不對 Google 做任何事。效果是這個字進入
追蹤清單：Argus 會檢查它有沒有出現在各頁的 Title、H1、Description、小標、網址與正文（字面比對，中文不
斷詞），每次掃描給出「最相關頁面與出現位置」，並和 Search Console 的相關搜尋詞做上面 Q42 的落差分析。
一句話：設為目標＝「從此這個字有人負責盯」，排名要靠你依建議修內容後再被 Google 重新評估。目標關鍵字
最多 20 個、每個 60 字，示範專案也能設定。

**Q44. 網站 head 裡的 `<meta name="keywords">` 有什麼用？Argus 怎麼利用它？**
對 Google 排名**沒有用**：Google 2009 年就公開表示不把它當排名訊號（1990 年代被塞字濫用，搜尋引擎早就不信
純自述、訪客看不到的標籤）。但它有一個別的來源給不了的價值：那是**網站主親手寫下的意圖**——「我希望被
這幾個字找到」。Argus 把它讀出來（逗號／分號分隔、跨頁去重、每頁最多 30 個），放在「搜尋關鍵字」分頁的
目標關鍵字表之下，和兩件事並排：(1) **頁面內容**：這個字有沒有真的出現在 Title／H1／Description／小標／
正文（和目標關鍵字同一套比對）；(2) **Search Console 實際搜尋詞**：有沒有人用這個字搜到你、排在第幾頁。
典型落差就是 demo 的亮點：宣告了「某課程名」卻沒有任何頁面把它放進標題，而真正帶來曝光的是另一個課程
名、根本不在清單裡。尚未設為目標的可一鍵加入追蹤。**不產生問題、不扣分**——Argus 不會因為沒有這個標籤
扣分，否則等於教人做無效的事；它只是意圖線索，結論仍靠頁面證據與 Search Console 數據。

**Q45. 你們的成本是多少？收益怎麼估算？**

變動成本只有 AI 功能，而且已經用計費設計轉嫁。** 數字分「事實」（程式碼／設定／實測）與「假設」（市價、
外推），完整版在 `docs/business-model-plan.md` 與設計文件第五章。

**Q46. GEO 檢測的核心是什麼？跟 SEO 差在哪？怎麼證明 AI 真的會引用？**
一句話：**GEO 在回答「生成式 AI（ChatGPT、Perplexity、Google AI 總覽）讀你的網站時，讀得到、讀得懂、
敢不敢引用？」**——三個問題，每項檢查都對得回其中一個：

| 問題 | 為什麼重要 | Argus 檢查什麼 |
|---|---|---|
| 讀得到嗎 | 多數 AI 爬蟲不執行 JavaScript；robots.txt 擋錯爬蟲等於自己消失 | 核心內容是否依賴 JS 才出現（原始 HTML 文字不到執行後的一半，中風險）；robots.txt 對 24 個 AI 爬蟲的政策（只擋訓練用不算問題，擋到 AI 搜尋／使用者觸發的才列）；llms.txt（新興做法，只提醒） |
| 讀得懂嗎 | AI 把頁面切成片段後檢索（RAG），結構決定能不能擷取乾淨的一段 | JSON-LD 與明確實體類型；`<main>`；長文有無小標題；段落過長、每個小標題區段超過約 280 字；列舉有沒有用清單 |
| 敢引用嗎 | 生成式引擎偏好有來源、有數據、有署名、有日期的內容 | 權威來源連結／參考資料、具體數據、引言；組織實體的 sameAs（維基／Wikidata／社群）；文章作者與日期、日期是否矛盾；內容是否可能過時 |

第 3 類依據 Princeton 等校「GEO: Generative Engine Optimization」（KDD 2024）：加入來源、數據、引言分別提升
被生成式引擎引用的可見度約 +27%／+33%／+41%，報告每項判定依據都附出處與限制。

- **跟 SEO 差在哪**：SEO 問「搜尋引擎會不會排你」，GEO 問「AI 會不會引用你」。交集是結構化資料；GEO 多了
  AI 爬蟲政策、可切塊結構、引用訊號三塊，SEO 完全不看。
- **分數會不會亂扣**：刻意保守——12 項裡 7 項資訊級不扣分、4 項低風險，只有「核心內容依賴 JS」是中風險
  （唯一會讓 AI 完全讀不到的問題）。GEO 訊號是加分空間不是錯誤，問題分析頁把它們放在「軟性建議」區。
- **怎麼證明 AI 真的會引用**（誠實邊界）：Argus 檢查的是內容訊號，不是量測 AI 實際行為；依據是公開研究，
  不是我們自己跑 ChatGPT 驗證。第一版全部規則式、零 token、可重現；「實際去問 AI 引擎有沒有引用你」是
  下一階段。
- **Demo 指給評審看**：問題分析頁「軟性建議」區；架構與信任頁的 AI 爬蟲政策表（24 個爬蟲分訓練／AI 搜尋／
  使用者觸發三類）；信任輪廓的身分／社群／學術／一致性四層就是 GEO 訊號的聚合；報告「核心內容高度依賴
  JavaScript 渲染」卡片的 `raw_html_text=565, rendered_text=1236`，數字就是證據。
- **一句話收尾**：SEO 讓搜尋引擎找到你，AEO 讓它答得出你，GEO 讓 AI 願意引用你——Argus 用可重現的規則
  檢查這三件事，不替 AI 代言，只告訴你訊號有沒有做到。

**Q47. AEO 檢測的核心是什麼？題目是 AI 出的嗎？分數怎麼來？**
一句話：**AEO 在回答「訪客（或 AI 助手）會問的問題，能不能在你網站上直接找到具體、可追溯原文的答案？」**
不是數 FAQPage／HowTo 標記（Google 已不支援），而是實際去找答案。

**題目不是 AI 出的，全程規則式、零 token。** 兩種來源：(1) 固定題庫 13 種意圖（電話、Email、地址、營業時間、
價格、報名方式、截止日期、資格、退款、配送、付款方式、預約、服務內容），只有正文命中觸發詞 2 次以上才出
那一題——所以每個網站題目不同，但出題是確定性的；(2) 網站自己寫的問句標題（「如何申請？」）直接當題。

**四層判定**（每題附原文與所在頁面）：

| 層 | 問什麼 | 失敗長什麼樣 |
|---|---|---|
| 1 取得內容 | 正文抓得到嗎（排除導覽、頁首、隱藏元素；要不要執行 JS 才出現） | 正文不到 100 字、題目不到 3 題 → 標「未充分評估」不給分 |
| 2 找到答案 | 哪一段在談這個主題（主題詞要出現；心得／見證段落不算） | 找不到 → 0 分 |
| 3 答案可用 | 值具不具體（電話號碼、金額、含年份的日期）、不同頁有沒有矛盾 | 空泛／沒年份 → 資訊不足 50%；不同頁價格或截止日不同 → 內容衝突 25% |
| 4 標記一致 | JSON-LD 寫的電話、地址在頁面上看不看得到；noindex／nosnippet 會不會讓答案無法被引用 | 逐頁問題，照常扣分 |

- **分數**：各題「權重 × 得分」的加權平均（聯絡電話、價格、截止日權重 1.0；Email、配送 0.6），再扣第 4 層的
  逐頁問題。整個網站沒談到的題庫題（例如沒有退貨）**不計分**，不會因為「不賣東西」被扣分。
- **可信度**：可回答的題另標「確認／可能／推測」——確認＝號碼、金額、日期等答案值逐字出現在原文；可能＝
  步驟或條件規則；推測＝只確認段落有具體敘述。只是說明，不影響分數。
- **引用可得性**：可回答的題另看那段能不能被 AI 引用——noindex、nosnippet、data-nosnippet 區塊＝無法引用；
  答案只在執行 JS 後才出現＝引用受限。
- **怎麼證明判定是準的**：人工標註的回歸資料集＋不拿來調規則的保留集，門檻精確率／召回率／準確率 ≥ 95%、
  誤判率 ≤ 5%，鎖在自動化測試裡，改規則不達標測試就失敗；另有人工校驗題集要求 100% 正確。
- **跟 SEO／GEO 差在哪**：SEO 看「頁面結構對不對」，GEO 看「AI 願不願意引用」，AEO 看「內容本身答不答得
  出問題」——同一個網站 SEO 滿分也可能 AEO 低分（有漂亮的 title，但找不到電話）。
- **誠實邊界**：第一版只做可重現的規則判定；受控 AI 評估（真的拿題目去問模型）與外部平台觀察尚未實作，報告
  不宣稱有。規則式判定會有語意誤判——實掃曾把「師資資格」當成「申請資格」的答案，這類案例會加進回歸資料集。
- **Demo 指給評審看**：AEO 問答分頁逐題表（判定、理由、原文）；報告第 5 章「AEO 問答檢測結果」；總覽的
  「可回答 5／資訊不足 2／無答案 1（可回答性 85 分）」一行。
