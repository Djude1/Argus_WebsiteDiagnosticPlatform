# 競賽 Word 文件同步規則

> **此規則的存在原因（真實事故）**：2026-09 競賽初賽 Q&A 時，複賽評審指出需求書內容與系統實際現況不同步——初賽版需求書定稿後系統持續演進，新增的功能、圖表與管理後台都沒有反映進文件。**競賽文件漂移與程式文件漂移同等嚴重：評審直接拿文件對照系統提問，文件講不出來就是失分。**

## 觸發條件（什麼異動要同步）

任何「改變對外可見事實」的功能異動，都必須同步本資料夾的內容 md：

- 新增功能（前台或管理後台）
- 新增／修改／移除 API 端點
- 新增／修改 model（牽動 ER 圖）
- 商業／計費邏輯異動（點數、方案、價格）
- 前端流程異動（使用者看得到的操作路徑）

判斷標準：**評審若拿最新版文件對照系統 demo，會不會發現落差？** 會，就要同步。

## 單一事實來源與檔案對應表

| 內容 | 單一事實來源檔 |
|---|---|
| 需求書全文內容 | [`需求書_複賽版完整內容.md`](需求書_複賽版完整內容.md) |
| 圖表／ER 圖／成本模組／架構圖 | [`設計文件_圖表與成本模組.md`](設計文件_圖表與成本模組.md) |
| 講解用差異（初賽→複賽改了什麼） | [`初賽與複賽差異對照.md`](初賽與複賽差異對照.md) |
| Word 檔本體 | repo 根目錄 `2026智慧創新競賽_Argus系統需求書_複賽版.docx`（由初賽版複製後逐次修訂） |

程式碼仍是所有事實的最終來源；上述 md 是「競賽文件觀點」的單一事實來源——**改 docx 之前必須先改 md**，兩者不得各自漂移。

## 同步流程（步驟化）

1. **功能 commit 同次更新對應內容 md**：改變對外可見事實的功能，在同一次 commit 內更新 `需求書_複賽版完整內容.md`（及／或 `設計文件_圖表與成本模組.md`）的對應小節。動筆前先以 `Grep` / `Read` 對照程式碼驗證事實（規則 B，見 [`docs/doc-sync-rules.md`](../docs/doc-sync-rules.md)）。
2. **文件交付點彙整修訂提示詞**：在複賽繳件前（或文件需定稿的時點），把累積的 md 變更彙整產出「小節修訂提示詞」。**每一段都必須提供完整替換文字**——Word Claude 看不到 repo 與程式碼，只寫「把某節更新成最新功能」這類描述它無從下手。
3. **人工貼給 Word Claude 套用**：由使用者把修訂提示詞貼給 Word 端 Claude，套用到 `2026智慧創新競賽_Argus系統需求書_複賽版.docx`。
4. **驗收**：套用完成後，在 docx 全文搜尋本次新增內容的關鍵字，確認新內容有出現；再搜尋被替換掉的舊錯誤字串，確認 **0 筆**，才算同步完成。

## 頁數／格式紅線

需求書必須維持官方範本結構與字型規範：字型、版面、頁數調整一律沿用 [`需求書_WordClaude提示詞.md`](需求書_WordClaude提示詞.md) 既有的 **P2（字型與版面）與 P3（白話化改寫）規範**，本檔不重複內容。修訂提示詞不得要求 Word Claude 更動 P2／P3 已定的格式。

## 禁止事項

- **不得跳過內容 md 直接改 docx 敘述**：docx 的每一次修訂都必須源自 md 的對應變更，否則 md 與 docx 會各自漂移，下次修訂提示詞就會蓋掉手工修改。
- **不得在 md 寫未經程式碼驗證的數字**：條目數、端點數、model 欄位、頁數等，動筆前一律對照程式碼或實跑結果（規則 B）。
